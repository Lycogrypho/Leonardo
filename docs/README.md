# Leonardo documentation site

The public support site (prose + tutorials + API reference) is published to
**GitHub Pages** from this folder:

> https://lycogrypho.github.io/Leonardo/

## Layout

| Path | Role |
|---|---|
| `docs/src/*.md` | The prose pages (single source, shared with the `mdoc`/Scaladoc pipeline). Each carries `title` + `nav_order` front matter that the [Just the Docs](https://just-the-docs.com) theme uses to build the sidebar. |
| `docs/src/*.svg` | Images referenced by the prose (`Banner.svg`, `logo_bw.svg`, `structure.svg`). |
| `docs/_config.yml` | Jekyll + Just the Docs configuration (remote theme, base URL, nav aux-links). |
| `docs/Gemfile` | Ruby gems for building the site (CI + local preview). **Includes `jekyll-include-cache`, which the theme needs and `remote_theme` does not install** -- see the note below. |
| `docs/structure.puml` | Source of `structure.svg` (regenerated by `sbt puml`). |
| `.github/workflows/pages.yml` | CI: builds the site and the Scaladoc API, then deploys to Pages. |

The **Scaladoc API reference** is not built by Jekyll — the workflow runs
`sbt "mdoc; doc; injectApiStyles"` and copies the generated API into the published
site under **`/api`** (with a `.nojekyll` marker so the `_`-prefixed class pages, e.g.
`_Solve.html`, are served verbatim).

## How it deploys

`.github/workflows/pages.yml` runs on every push to `main` that touches the docs,
sources, or build:

1. `sbt "mdoc; doc; injectApiStyles"` — verifies the `scala mdoc` code samples in the
   prose, renders the Scaladoc API, and applies the logo/CSS.
2. `bundle exec jekyll build --source src --destination ../_site --config _config.yml`
   — renders the prose into `_site` with the Just the Docs theme.
3. Copies `target/scala-3.3.6/api` into `_site/api` and drops `_site/.nojekyll`.
4. Uploads `_site` and deploys it with `actions/deploy-pages`.

### A trap worth knowing: `remote_theme` does not install the theme's gems

`remote_theme` downloads the theme's **files** (layouts, includes, sass) and nothing else.
A theme's runtime gem dependencies are *not* resolved on your behalf, so any Liquid tag the
theme's templates use has to be in **our** `Gemfile` and **our** `plugins:` list.

Just the Docs declares `jekyll-include-cache` as a runtime dependency, and its
`_includes/head.html` and `_includes/components/breadcrumbs.html` both use the
`{% include_cached %}` tag that gem provides.  Since our `_config.yml` gives every page
`layout: default`, and `default.html` includes both of those, a missing
`jekyll-include-cache` fails the build on the very first page with:

```
Liquid Exception: Unknown tag 'include_cached' in /_layouts/default.html
```

This is what broke the Pages deployment on every run from the workflow's introduction until
2026-08.  If the theme adds another plugin dependency later, the same thing will happen
again — check `just-the-docs.gemspec` for `add_runtime_dependency` lines and mirror any
Liquid-tag-providing gem into both files here.

The `jekyll build` step passes `--trace` so that a failure of this kind prints a backtrace
instead of a bare `exit code 1`.
### One-time repository setup (manual)

GitHub Pages must be told to serve the Actions artifact:

> **Settings → Pages → Build and deployment → Source = "GitHub Actions"**

After that, every push to `main` republishes the site automatically. No local
toolchain is required.

## Local preview

Requires Ruby (3.x) and Bundler:

```bash
cd docs
bundle install
bundle exec jekyll serve --source src --config _config.yml
# → http://127.0.0.1:4000/Leonardo/
```

To preview the API alongside it, run `sbt "mdoc; doc; injectApiStyles"` and copy
`target/scala-3.3.6/api` into the served tree under `api/`.
