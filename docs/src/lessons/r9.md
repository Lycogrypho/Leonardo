# R9 — Your session

**Goal:** keep work between visits, hand it to someone else, and set the REPL up the way you
like it.

## What a session actually is

```scala mdoc:passthrough
lesson.show("k := 5", "damped := exp(-k*t) * sin(t)", "env")
```

Everything you have set — bindings, definitions, settings — **can be written back out as the
commands that would recreate it.** That is the whole persistence mechanism.

### Why a script rather than a snapshot?

Because a script is something you can read, edit, diff and send. A saved session is plain text
in the same language you have been typing; `:load` does not restore a snapshot, it **replays the
commands**. One consequence is worth noticing: saving, loading and sharing are not three
features, they are one idea used three ways.

It is also why the order inside a saved file matters — settings are written before bindings, so
that a script re-enables `exact` *before* it parses the values that need it ([R8](r8.md)).

## Saving and loading

At the terminal prompt:

```text
> :save work.leo
saved to work.leo
> :load work.leo
```

In the **browser** the same two commands work, but there is no file system, so the name is a key
in the browser's own storage — `:save work`, then `:load work`, in the same browser on the same
site. The spelling is deliberately identical: two builds of one REPL should not speak two
command languages.

## Sharing a link

The browser REPL's **Share** button encodes your whole session into the address — specifically
into the part after `#`, which browsers never send to a server, so your work stays on your
machine. Anyone opening that link arrives with your bindings and settings already in place.

It is the fastest way to ask someone a question about a calculation: send the link, not a
screenshot of it.

## Settings worth knowing

Each reports its state when typed bare, and each is saved with the session:

```scala mdoc:passthrough
lesson.show("pretty", "latex", "names", "exact", "logic")
```

You have met `pretty` ([R6](r6.md)) and `exact` ([R8](r8.md)). Two more are worth a moment.

## `names on` — the typo catcher

[R2](r2.md) showed that an unknown name is a perfectly good variable, so a misspelling cannot be
an error. `names on` makes it visible instead:

```scala mdoc:passthrough
lesson.show("names on", "velocty + 1")
```

The note announces every newly-seen free variable — so a typo shows up as a name you did not
intend to create. It is **off by default** because in a computer algebra system a new free
variable is the normal case, not a suspicious one; turn it on while you are working with concrete
quantities, off when you are doing algebra:

```scala mdoc:passthrough
lesson.show("names off")
```

## `latex on` — a second channel

```scala mdoc:passthrough
lesson.show("latex on", "(a + b)/(c + d)", "latex off")
```

**The text is identical either way**, which is the point — and it is why this page shows no
difference. The typeset formula travels on a *second* channel that only a front end able to
render it picks up. In the browser you would see the fraction properly set **beside** the line
above, never instead of it: the text is the canonical form you would have to retype, so it is
the one thing that may not be hidden.

`pretty` and `latex` exclude each other — turning one on turns the other off — because both are
ways of laying a matrix out, and doing both at once would show the same thing twice.

## Starting clean

```scala mdoc:passthrough
lesson.show("unset damped", "unset k", "env")
```

You are about to work with measured quantities and want typos caught. Turn on the diagnostic,
then evaluate `tempreature * 2` and see what it tells you.

## What you learned

- **A session is a replayable script**, which is why `:save`, `:load` and Share are one idea.
- The browser uses its own storage instead of files; the commands are spelled the same.
- A share link carries the session in the URL fragment, which never leaves your machine.
- **`names on` catches the typo-becomes-variable trap**; `latex on` adds typeset output beside
  the text, never instead of it.
- Settings are saved with the session, and written before the bindings that depend on them.
