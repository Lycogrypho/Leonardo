# L10 — A small application, end to end

**Goal:** build one real thing. Nine lessons of pieces, assembled into a program that takes a
function typed by a person and reports what can be said about it — and that behaves properly
when the answer is *nothing*.

```scala mdoc:silent
import it.grypho.scala.leonardo.core.*
import it.grypho.scala.leonardo.scalar.*
import it.grypho.scala.leonardo.scalar.Syntax.*
import it.grypho.scala.leonardo.equation.{_Equation, solve}
import it.grypho.scala.leonardo.parser.Parser
```

## What we are building

`analyse(text, variable)` → a report carrying the derivative, the stationary points, an
antiderivative where one exists, and a few sampled values. Text in, a typed record out, every
refusal represented rather than hidden.

The interesting design question is not *how* — every piece is one call from an earlier lesson —
but **what the record is allowed to contain**. Get that wrong and the whole thing lies.

## The record

```scala mdoc:silent
case class Report(
    input:          String,
    expression:     _Expression,
    variables:      List[String],
    derivative:     Option[_Expression],      // None: no rule fired
    stationary:     Option[List[_Expression]],// None: could not be asked; Some(Nil): none exist
    antiderivative: Option[_Expression],      // None: not in closed form
    samples:        Vector[(Double, Double)]
)
```

Three of the fields are `Option`, and one is an `Option` of a `List` — which is the field worth
pausing on. **`None` and `Some(Nil)` are different answers**: *we could not look for stationary
points* against *we looked and there are none*. Collapsing them to an empty list would make a
failed derivative indistinguishable from a monotonic function, which is L9's rule about not
papering over a refusal, applied at the level of a data structure.

## The pieces

L1's reader, converting the foreign `ParseResult` at the boundary:

```scala mdoc:silent
def read(text: String): Either[String, _Expression] =
  val parsed = Parser.parse(text)
  if parsed.successful then Right(parsed.get)
  else Left(s"parse error: ${parsed.toString.linesIterator.next()}")
```

L5's traversal, twice, for L6's give-up convention:

```scala mdoc:silent
def contains(e: _Expression)(p: _Expression => Boolean): Boolean =
  p(e) || e.children.exists(contains(_)(p))

def hasDerivative(e: _Expression): Boolean = contains(e)(_.isInstanceOf[_Derivative])
def hasIntegral(e: _Expression):   Boolean = contains(e)(_.isInstanceOf[_Integral])
```

And L6's numeric check, because expression equality is structural and would reject a correct
antiderivative:

```scala mdoc:silent
def agreesAt(a: _Expression, b: _Expression, v: _Variable, pts: List[Double]): Boolean =
  pts.forall: p =>
    val env = Environment().withBinding(v.variable, _Number(p))
    (a.eval(env), b.eval(env)) match
      case (Right(_Number(p1)), Right(_Number(p2))) => math.abs(p1 - p2) < 1e-9
      case _                                        => false
```

## Assembling

```scala mdoc:silent
def analyse(text: String, v: _Variable): Either[String, Report] =
  read(text).map: e =>
    val d = e.derive(v).simplifyFully()
    val derivative = Option.unless(hasDerivative(d))(d)

    val stationary = derivative.map: dv =>
      solve(_Equation(dv, _Number(0)), v, Environment()).map(_.rhs)

    val anti = e.integrate(v).simplifyFully()
    val antiderivative =
      Option.when(!hasIntegral(anti) && agreesAt(anti.derive(v), e, v, List(0.3, 1.7)))(anti)

    Report(
      input          = text,
      expression     = e,
      variables      = e.freeVars.toList.sorted,
      derivative     = derivative,
      stationary     = stationary,
      antiderivative = antiderivative,
      samples        = e.sample(v, -2, 2, 5)
    )
```

Nineteen lines, and **every refusal in it is load-bearing**: `Option.unless` on the derivative,
`.map` on the stationary points so they inherit the derivative's absence, and `Option.when` with
a numeric verification on the antiderivative.

## Running it

A polynomial, where everything closes:

```scala mdoc
analyse("x^3 - 3*x", _Variable("x"))
```

Now something whose antiderivative is not elementary:

```scala mdoc
analyse("exp(x^2)", _Variable("x")).map(_.antiderivative)
```

```scala mdoc
analyse("exp(x^2)", _Variable("x")).map(_.derivative.isDefined)
```

The derivative is there and the integral is not, reported separately — which is the whole reason
they are separate fields.

And input that never becomes an expression at all:

```scala mdoc
analyse("sin(", _Variable("x"))
```

## Rendering it

The record is the product; presenting it is a second, separable job — and this is where L7's
display rule lands:

```scala mdoc:silent
def render(r: Report): String =
  val lines = List(
    s"input:      ${r.input}",
    s"parsed:     ${r.expression}",
    s"variables:  ${r.variables.mkString(", ")}",
    s"derivative: ${r.derivative.fold("— no rule applies")(_.toString)}",
    s"stationary: ${r.stationary.fold("— not determined") {
         case Nil  => "none"
         case sols => sols.mkString(", ")
       }}",
    s"integral:   ${r.antiderivative.fold("— not in closed form")(_.toString)}",
    // _Number(_).display, never f"%.3f": see the note below.
    s"samples:    ${r.samples.map((a, b) => s"(${_Number(a).display(1)}, ${_Number(b).display(3)})").mkString(" ")}"
  )
  lines.mkString("\n")
```

```scala mdoc
analyse("x^3 - 3*x", _Variable("x")).map(render).foreach(println)
```

```scala mdoc
analyse("exp(x^2)", _Variable("x")).map(render).foreach(println)
```

Two reports, the same shape, and **the second is honest about its two gaps instead of omitting
the rows**. A reader can tell the difference between "there is no antiderivative" and "this
program did not try", which is the property the whole design was arranged around.

Note where the rounding happens: the samples are full `Double`s in the record and are formatted
only in `render`, which is L3's rule — never round a value before storing it.

**And note how.** The obvious `f"($a%.1f, $b%.3f)"` is wrong here, and this page caught it: the
`f` interpolator formats through the *default locale*, so on a machine set to Italian it printed
`(-2,0, -2,000)` and would have printed `(-2.0, -2.000)` on the Linux runner that publishes the
site — the same document rendering differently depending on who built it. `_Number(d).display(p)`
goes through the library's own renderer, which is locale-independent *and* platform-independent;
the second matters because Scala.js renders a bare `Double` the JavaScript way. **If you are
formatting a number out of this library, ask the library to do it.**

## What this deliberately does not do

Worth stating, because each is the moment you would reach for a further lesson or a further
package:

- **No classification of the stationary points.** That needs the second derivative's sign at
  each root — `e.deriveN(v, 2)` and an evaluation, which is an exercise below.
- **No domain analysis.** `domain(e, x)` would say where the function is defined at all, and the
  samples silently drop non-finite points today.
- **No plotting.** The samples are the data a plotter takes; the browser REPL draws them.
- **It analyses one variable.** `variables` reports the others, and a second free name makes
  every numeric row above depend on a binding nobody supplied.

Each is a small addition to the same record — which is what the record being a plain case class
buys.

## Try it yourself

Add a `classified: List[(String, String)]` field pairing each stationary point with `"minimum"`,
`"maximum"` or `"inflection"`, from the sign of the second derivative there.

<details>
<summary>Answers</summary>

```scala mdoc:silent
/** Classifies a stationary point by the sign of the second derivative at it. */
def classify(e: _Expression, v: _Variable, at: _Expression): String =
  val second = e.deriveN(v, 2).simplifyFully()
  at.eval(Environment()) match
    case Right(_Number(p)) =>
      second.eval(Environment().withBinding(v.variable, _Number(p))) match
        case Right(_Number(d)) if d > 1e-12  => "minimum"
        case Right(_Number(d)) if d < -1e-12 => "maximum"
        case Right(_Number(_))               => "inflection (second derivative vanishes)"
        case _                               => "undetermined"
    case _ => "undetermined (point is not numeric)"
```

```scala mdoc
analyse("x^3 - 3*x", _Variable("x")).map: r =>
  r.stationary.getOrElse(Nil).map(p => p.toString -> classify(r.expression, _Variable("x"), p))
```

A minimum at `1` and a maximum at `-1`, which is right for `x³ − 3x`.

Two details that are the lesson rather than the calculus. The **tolerance** is unavoidable: the
second derivative at a stationary point is a computed `Double`, so `> 0` would classify numerical
noise, and `1e-12` is a threshold you have chosen and should be able to defend. And the
**`case _ => "undetermined"`** arms are not padding — a symbolic root (from a solver given
symbolic coefficients) is a perfectly ordinary outcome here, and this function refuses it the way
the library would rather than forcing a number out of it.
</details>

## What you learned

- **Design the record before the code.** `Option[List[…]]` for the stationary points is the whole
  design: `None` and `Some(Nil)` are genuinely different answers, and merging them would have
  made the program lie.
- Every piece was one call from an earlier lesson — reading at the boundary (L1), traversal for
  the give-up convention (L5), numeric rather than structural verification (L6), refusals kept
  distinct (L9).
- **Formatting is a separate job from computing.** Full `Double`s in the record, rounding only in
  `render`.
- A program built this way **degrades one field at a time**: a declined integral costs you the
  integral and nothing else.
