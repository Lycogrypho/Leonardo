# R2 — Expressions and free variables

**Goal:** understand why an unknown name is a perfectly good answer, learn the two commands that
rearrange an expression, and meet the two places the notation will surprise you.

## A name you have not defined is not an error

```scala mdoc:passthrough
lesson.show("y")
```

`y` is a **free variable** — it stands for itself. In most languages that would be an error
("undefined"); here it is the ordinary case, because algebra is mostly about quantities whose
value you do not know yet.

[R1](r1.md) put the rule as *"a number when one exists, an expression when it does not"*. Here
is the same rule with both halves side by side:

```scala mdoc:passthrough
lesson.show("2 * 3 + 1", "2 * y + 1")
```

The second line did not fail. There was simply nothing left to do once `y` turned out to be
unknown, so the answer is the expression itself.

## Why so many brackets?

`2 * y + 1` came back as `((2.0 * y) + 1.0)` — every operation parenthesised, nothing left to
precedence. That is deliberate: **an answer is always valid input**. You can copy any result
straight back to the prompt and get the same thing again:

```scala mdoc:passthrough
lesson.show("((2.0 * y) + 1.0)")
```

It is the same property that lets a whole session be saved as a text file and replayed
([R9](r9.md)), so the brackets are worth the visual noise.

## Rearranging: `simplify` and `expand`

Plain evaluation rearranges nothing — it computes what it can and stops. Two commands do the
rearranging, and each does exactly one job.

`simplify` applies structural rules: identities, constant folding, inverse pairs.

```scala mdoc:passthrough
lesson.show("y + y", "simplify y + y", "simplify x * 1 + 0", "simplify ln(exp(z))")
```

`expand` distributes products over sums:

```scala mdoc:passthrough
lesson.show("expand 2 * (x + 3)")
```

Notice `2 * 3` came back unfolded. `expand` distributes and nothing else; folding constants is
`simplify`'s job. Each command does one thing, and you choose which.

### What `simplify` will not do

```scala mdoc:passthrough
lesson.show("simplify 2x + 3x")
```

It left that alone. **`simplify` is a single structural pass, not an algebraic normal form**, so
it will not gather unlike-looking terms for you. Knowing where it stops saves an argument with
it later — and when you need a polynomial genuinely tidied, `expand` followed by `simplify` gets
most of the way.

## Trap 1 — a space between two names is load-bearing

Juxtaposition means multiplication, so a number beside a name is a product, and so are two names
**separated by a space**:

```scala mdoc:passthrough
lesson.show("2 y", "theta phi")
```

Close the space, though, and it is no longer two names at all:

```scala mdoc:passthrough
lesson.show("thetaphi", "simplify thetaphi - theta * phi")
```

`thetaphi` is **one variable with a long name**, and the subtraction does not cancel because the
two expressions have nothing in common.

The rule is unavoidable rather than careless: a name may be several characters long, so `ab` has
to mean *something*, and reading it as one name is the only choice that does not make `alpha`
mean `a*l*p*h*a`. The practical form is simple — **write `*`, or at least a space, between two
names** — and the failure is silent, because both readings are legitimate expressions.

## Trap 2 — an unknown function name becomes a variable

Writing a function's own name alone is an error, because the grammar has claimed it:

```scala mdoc:passthrough
lesson.show("sin")
```

But a name the grammar has **not** claimed is just a variable — even when you write it like a
call:

```scala mdoc:passthrough
lesson.show("sqrt(9)")
```

That is `sqrt * 9`: the variable `sqrt` times nine, because there is no `sqrt` function in this
language and juxtaposition is multiplication.

**The grammar cannot refuse it, so the REPL warns instead.** The note is not an error — the
expression is valid and will evaluate, simplify and save perfectly well. It is there because a
name written immediately before `(` is almost never meant as a product, and a silent product
would be a confident answer to a question you never asked.

Square roots are powers:

```scala mdoc:passthrough
lesson.show("9^0.5", "9^(1/2)")
```

That warning fires on **call syntax only**. For a bare unknown name — an ordinary typo — there
is a second diagnostic you can switch on, and [R9](r9.md) does.

## Try it yourself

Predict each answer before you run it: `cos`, `16^0.25`, `a b`, `ab`, `simplify (x + 0) * 1`.

<details>
<summary>Answers</summary>

```scala mdoc:passthrough
lesson.show("cos", "16^0.25", "a b", "ab", "simplify (x + 0) * 1")
```

`a b` is a product of two variables; `ab` is a single variable. One space is the whole
difference, and nothing warns you about it.
</details>

## What you learned

- A free variable is an ordinary answer, not a failure.
- **Answers are fully parenthesised because an answer is valid input** — you can paste one back.
- `simplify` applies structural rules; `expand` distributes. **Neither is a normal form**, and
  `simplify` will not collect `2x + 3x`.
- **`theta phi` is a product; `thetaphi` is one variable.** The space is load-bearing, and
  nothing warns you.
- **An unknown function name becomes a variable**, and the REPL warns when it looks like a call.
  The radical is `x^(1/2)`.
