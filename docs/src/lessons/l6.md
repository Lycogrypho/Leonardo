# L6 — The calculus API

**Goal:** differentiate, integrate and tidy an expression from code — and read the answer
correctly when the library declines to do what you asked.

```scala mdoc:silent
import it.grypho.scala.leonardo.core.*
import it.grypho.scala.leonardo.scalar.*
import it.grypho.scala.leonardo.scalar.Syntax.*
import it.grypho.scala.leonardo.parser.Parser

// L1's reader, unchanged.
def expr(text: String): _Expression =
  val parsed = Parser.parse(text)
  if parsed.successful then parsed.get
  else sys.error(s"lesson input failed to parse: $text")

val x = _Variable("x")
val y = _Variable("y")
```

## They are all the same shape

```scala
def derive(e: _Expression, v: _Variable): _Expression
def integrate(e: _Expression, v: _Variable): _Expression
def simplify(e: _Expression): _Expression
def expand(e: _Expression): _Expression
def normalize(e: _Expression, v: _Variable): _Expression
```

Expression in, expression out. Note what is **not** in any of those signatures: no
`Environment`, and no `Either`. These are syntactic transformations on a tree — they do not
consult bindings, they do not evaluate, and they cannot fail in the sense L2 meant. Everything
about how they refuse is in the returned expression, which is what most of this lesson is about.

`Syntax` makes them method calls, and chains read better that way:

```scala mdoc
expr("x^2").derive(x)
```

**Once you import `Syntax`, use the method form and not the function form.** Importing both
`scalar.*` and `scalar.Syntax.*` puts two `derive`s in scope, and a bare `derive(e, x)` then
fails to compile with *"reference to derive is ambiguous"*. It is not a clash worth avoiding by
dropping either import — just pick the method form and stay with it, which is what the rest of
this page does.

## `derive`

Simple shapes come back already clean, because the rule table builds its results through smart
constructors that drop the `1`s and `0`s as it goes:

```scala mdoc
expr("x^3 + sin(x)").derive(x)
```

That tidiness is local, though, and it stops at the node. A rule that assembles a larger
expression leaves whatever its pieces happened to be — here the general power rule:

```scala mdoc
expr("x^x").derive(x)
```

Nothing is wrong with that; it is the derivative. But differentiating and simplifying are
separate passes, so the tidying is yours to ask for:

```scala mdoc
expr("x^x").derive(x).simplifyFully()
```

**Get into the habit of that pair.** A raw derivative grows fast, and the growth compounds if you
differentiate again without tidying in between.

Higher-order and mixed partials have their own entry points rather than being your fold:

```scala mdoc
expr("x^4").deriveN(x, 2).simplifyFully()
```

```scala mdoc
expr("x^2 * y^3").derive(x, y).simplifyFully()
```

`deriveN(v, n)` repeats one variable; the varargs `derive(e, v1, v2, …)` folds left to right, so
`derive(f, x, y)` is ∂/∂y(∂f/∂x) and `derive(f, x, x)` is the second derivative in `x`.

`derive` is **memoised** on `(expression, variable)` — it is pure, and expressions are immutable
structural keys, so re-differentiating a shared sub-tree is free. You never need to cache it
yourself.

## The give-up convention

Here is the thing to learn before you use any of this in anger. Not every expression has a
derivative in the rule table:

```scala mdoc
expr("digamma(x)").derive(x)
```

It did not throw, it did not return `None`, and it did not lie. **It returned the `_Derivative`
node itself** — *"the derivative of `digamma(x)`"* is a perfectly good answer to *"what is the
derivative of `digamma(x)`?"*, and it is the honest one when the engine has no rule. Every
functional in the library does this: a fixpoint rather than a failure.

The frontier is visible if you look at the neighbouring function. `Gamma` **does** differentiate,
by `Γ(x)·ψ(x)`:

```scala mdoc
expr("Gamma(x)").derive(x)
```

It differentiates precisely because digamma exists as a node to write the answer in — and
digamma does not, because trigamma is not implemented. Every rule table ends somewhere, and
that edge is a fact about this library rather than about mathematics.

The cost is that a caller has to *look*, and the library never does it for you. So write the
check, which is L5's traversal and three lines:

```scala mdoc:silent
/** True when `e` still contains an unevaluated derivative. */
def containsDerivative(e: _Expression): Boolean = e match
  case _: _Derivative => true
  case other          => other.children.exists(containsDerivative)
```

```scala mdoc
containsDerivative(expr("x^3").derive(x))
```

```scala mdoc
containsDerivative(expr("digamma(x)").derive(x))
```

That is exactly how the library guards itself: a Taylor expansion aborts entirely if any
coefficient still contains a `_Derivative`, because **a series carrying an unevaluated derivative
is worse than no series at all**. Adopt the same rule — check at the boundary of your own
computation, and refuse rather than pass a half-answer downstream.

## `integrate`

The counterpart, and much more likely to decline:

```scala mdoc
expr("2*x + cos(x)").integrate(x)
```

Two things to notice. There is **no constant of integration** — the result is *an*
antiderivative, and inventing a `+ C` as a free variable would put a name into your expression
that you would then have to explain to everyone reading it. And again nothing tidied up:

```scala mdoc
expr("2*x + cos(x)").integrate(x).simplifyFully()
```

When no rule fires you get the same fixpoint you got from `derive`:

```scala mdoc
expr("exp(x^2)").integrate(x)
```

```scala mdoc:silent
/** True when `e` still contains an unsolved indefinite integral. */
def containsIntegral(e: _Expression): Boolean = e match
  case _: _Integral => true
  case other        => other.children.exists(containsIntegral)
```

```scala mdoc
containsIntegral(expr("exp(x^2)").integrate(x))
```

That expression genuinely has no elementary antiderivative, so the refusal is the mathematics
and not a gap. But you cannot tell those two apart from the outside, and you do not need to —
either way the answer is *"not in closed form"*, and your code takes the same branch.

### Check an antiderivative by differentiating it back

This is the cheapest correctness test you can run against an integral, and it is what the
library's own rule-table harness does for every rule it ships. The obvious way to write it does
not work, and finding out why is worth the detour — compare the derivative of the antiderivative
with the integrand, structurally:

```scala mdoc
expr("2*x").integrate(x).derive(x).simplifyFully() == expr("2*x").simplifyFully()
```

The antiderivative is perfectly correct and the test says no. `∫2x` comes back as `2·(x²/2)`,
whose derivative is `2·(2x/2)` — equal to `2x` as a number at every point, and a different tree.
**`==` on expressions is structural equality**, and two expressions being equal *as functions* is
not something a structural comparison can see.

So compare values, not shapes:

```scala mdoc:silent
/** True when `a` and `b` agree numerically at every sample point. */
def agreesAt(a: _Expression, b: _Expression, v: _Variable, points: List[Double]): Boolean =
  points.forall: p =>
    val env = Environment().withBinding(v.variable, _Number(p))
    (a.eval(env), b.eval(env)) match
      case (Right(_Number(p1)), Right(_Number(p2))) => math.abs(p1 - p2) < 1e-9
      case _                                        => false

/** An antiderivative of `text` in `v`, verified by differentiating it back. */
def antiderivative(text: String, v: _Variable): Option[_Expression] =
  val f      = expr(text)
  val result = f.integrate(v)
  Option.when(!containsIntegral(result) && agreesAt(result.derive(v), f, v, List(0.3, 1.7, 2.9)))(result)
```

```scala mdoc
antiderivative("2*x", x)
```

```scala mdoc
antiderivative("cos(x)", x)
```

```scala mdoc
antiderivative("exp(x^2)", x)
```

Two refusals with different meanings, and the function collapses them deliberately: the first
two closed and verified, the third never closed at all. Sampling is not a proof — a handful of
points cannot distinguish two functions that agree on them — but for catching a wrong
antiderivative it is both sufficient in practice and the only thing that scales.

## `simplify` and `simplifyFully`

`simplify` is **one structural pass**: identity and absorbing elements, constant folding,
same-operand rules (`x + x → 2x`, `x * x → x^2`), double negation, inverse function pairs, and
known values at zero.

```scala mdoc
expr("x + 0 + 1*x").simplify()
```

`simplifyFully` iterates it to a fixpoint, which terminates because a pass never makes an
expression bigger. **In your own code, call `simplifyFully`** — a single pass is what the library
composes internally, not what a caller usually wants.

Now the three things it does not do, each of which catches people.

**It does not cancel common factors.** It is a structural rewriter, not a normal form, and
nothing in it knows how to divide:

```scala mdoc
expr("(x^2 - 1)/(x - 1)").simplifyFully()
```

**It does not evaluate.** `simplify` and `eval` are different passes, so a functional node stays
a node no matter how fully you simplify it:

```scala mdoc
_Derivative(expr("sin(x)"), x).simplifyFully()
```

```scala mdoc
_Derivative(expr("sin(x)"), x).eval(Environment())
```

Both are right, and they answer different questions — *tidy this tree* against *work this out*.
(The REPL's `simplify` command runs the second pass for you, which is why a prompt session and a
library call can look as though they disagree.)

**It ignores bindings**, having no environment to read them from:

```scala mdoc
expr("x + x").simplifyFully()
```

That is not a limitation — it is what makes simplification safe to run on an expression you are
going to evaluate later, under an environment you do not have yet.

## `expand` and `normalize`

`expand` distributes `*` over `+` and expands integer powers, and — the part everyone trips on —
**does not collect like terms**:

```scala mdoc
expr("(x + 1)*(x + 2)").expand().simplifyFully()
```

The product is multiplied out and the two `x` terms are still sitting apart. Collecting them is
a different question, because it needs to be told *which variable the polynomial is in*:

```scala mdoc
expr("(x + 1)*(x + 2)").expand().normalize(x)
```

Underneath is `collect`, which hands you the dense coefficient vector, lowest degree first — the
same shape L4's `polynomial` builder consumes, so the two compose into a round trip:

```scala mdoc
expr("(x + 1)*(x + 2)").expand().collect(x)
```

And it returns an `Option` because not everything is a polynomial. This is the one function in
the lesson that refuses with `None` rather than with a node, because "the coefficients of
`sin(x)` in `x`" is not a question with an unhelpful answer — it is a question with no answer:

```scala mdoc
expr("sin(x)").collect(x)
```

`normalize` on the same input returns it **unchanged** rather than failing, which is the
convention everywhere else. Two functions, two refusal styles, and the `Option` is the one to
reach for when you need to branch.

## Try it yourself

Write `stationaryPoints(text: String, v: _Variable): Option[List[_Expression]]` — differentiate,
and solve the derivative for zero. Return `None` if the derivative did not close.
`equation.solve(eq, v, env)` returns a `List[_Equation]` in the shape `v = expr`, and
`_Equation(lhs, rhs)` builds the equation.

<details>
<summary>Answers</summary>

```scala mdoc:silent
import it.grypho.scala.leonardo.equation.{_Equation, solve}

def stationaryPoints(text: String, v: _Variable): Option[List[_Expression]] =
  val d = expr(text).derive(v).simplifyFully()
  Option.when(!containsDerivative(d)):
    solve(_Equation(d, _Number(0)), v, Environment()).map(_.rhs)
```

```scala mdoc
stationaryPoints("x^2 - 4*x + 1", x)
```

```scala mdoc
stationaryPoints("x^3 - 3*x", x)
```

```scala mdoc
stationaryPoints("digamma(x)", x)
```

The three outcomes are the three you have to handle everywhere in this library: one answer, more
than one answer, and *the question could not be reached*. Note that the last is `None` because
**we** decided to make it one — `derive` handed back a `_Derivative` node, and solving that for
zero would have produced a confident and meaningless list.

The `simplifyFully` before solving is cheap insurance rather than decoration. The solver reads
coefficients through `collect`, which recognises polynomial *structure* — and while this
particular derivative arrives clean, the `x^x` case above is what a leftover `x/x` in the middle
of one looks like. Tidying first costs a pass and removes the question.
</details>

## What you learned

- The calculus functions are **expression in, expression out** — no environment, no `Either`.
  They transform trees; they do not evaluate them.
- **Derivatives and integrals come back untidy.** `derive` then `simplifyFully` is the pair to
  reach for, and `derive` is memoised so repeating it is free.
- **The give-up convention: an unsolved functional is returned as itself.** Nothing throws and
  nothing returns `None`, so *you* must check — a three-line traversal over `children`, and the
  same one the library uses to guard its own series expansions.
- `integrate` yields **an** antiderivative with **no `+ C`**, and differentiating the result back
  is the cheapest test you can write against it.
- `simplify` is **structural**: no common-factor cancellation, no evaluation of functionals, and
  no knowledge of bindings. Call `simplifyFully`; use `eval` when you want the arithmetic done.
- `expand` multiplies out and **leaves like terms uncollected** — `normalize(v)` collects them,
  and `collect(v)` gives the coefficient vector as an `Option`, the one refusal here that is not
  a node.
